## 1. HTML、JavaScript、PHP 的区别

### 一句话分工

| | **HTML** | **CSS** | **JavaScript** | **PHP** |
|---|---|---|---|---|
| 全称 | HyperText Markup Language | Cascading Style Sheets | JavaScript | PHP: Hypertext **P**reprocessor |
| **类别** | **标记语言**（不是编程语言） | 样式语言 | **编程语言** | **编程语言** |
| **在哪跑** | **浏览器** | **浏览器** | **浏览器** | **服务器** |
| **管什么** | 页面上**有什么** | **长什么样** | **怎么动** | 生成 HTML、读写数据库 |
| **代码谁看得到** | 用户（Ctrl+U） | 用户 | **用户** | **谁也看不到** |
| 能连数据库吗 | ❌ | ❌ | ❌ | ✅ |
| 出错时 | **容错**，凑合显示 | 跳过那一条 | **报错**，后面不执行 | **报错**，500 |

**两个容易搞错的点：**

1. **HTML 不是编程语言** —— 它没有变量、循环、判断，只是给内容**贴标签**。
2. **JavaScript 和 Java 没关系** —— 名字像，是当年蹭热度。**JS 跑在浏览器里。**

### 实测证据（用 DVWA 的两份真实响应数的）

| 搜索串 | 反射型响应 | DOM 型响应 | 说明 |
|---|---|---|---|
| `<?php` / `$_GET` / `echo` | **0** | **0** | **PHP 源码永远不发给浏览器** |
| `<script` | 3 | 3 | **JS 会发过来**（所以你看得到它的源码） |
| `document.write` | 0 | **6** | DOM 型那段 JS 是明文躺在响应里的 |
| `alert(1)` | **1** | **0** | ★ 反射型是**服务器**拼的；DOM 型**服务器没拼** |

**还实测过：** 直接访问 `.../xss_d/source/low.php` → **HTTP 200，长度 0 字节**。
服务器**执行**了它，它没产出东西 → **你永远拿不到 PHP 源码。**

### ★ 一句话记住

> **服务器跑 PHP，浏览器跑 HTML/CSS/JS —— 两拨代码，两台机器。**
> **服务器发完响应就"死"了；页面之后的一切（DOM、弹窗、请求）都是浏览器在干。**

## 2. 三种 XSS 的区别

### ★ 只用一个问题就能分清

> ### 「那段 HTML 字符串，是在**哪里**被拼出来的？」

```text
payload 有没有被【服务器】拼进返回的 HTML？
│
├─ 有 ──→ 那它从哪来？
│          ├─ 本次请求（URL / body）   ──→  反射型
│          └─ 数据库（之前存进去的）   ──→  存储型
│
└─ 没有 ─→ 那是谁拼的？──→ 浏览器里的 JS ──→  DOM 型
```

### 完整对照表

| 维度 | **反射型** | **存储型** | **DOM 型** |
|---|---|---|---|
| **payload 从哪来** | 本次请求（URL / body） | **数据库**（之前存的） | 浏览器地址栏 / fragment |
| **谁拼接** | **服务器（PHP）** | **服务器（PHP）** | **浏览器（JS）** |
| **服务器响应里有 payload 吗** | ✅ 有 | ✅ 有（从库里读出来） | ❌ **没有** |
| **受害者怎么中招** | 点攻击者给的链接 | **打开页面就中** | 点攻击者给的链接 |
| **能持续多久** | 一次性 | **持久**（除非删库） | 一次性 |
| **payload 在日志里** | ✅ URL（请求行） | ❌ **POST body** | ⚠️ `?` 里可见；`#` 里完全不可见 |
| **修在哪一层** | 服务器：输出编码 | 服务器：输出编码 | **前端**：别用 `innerHTML` / `document.write` |
| **DVWA Low 的 PHP** | `echo` 直拼 | `echo` 直拼（⚠️ 只做了 SQL 层转义） | **空的** |

### 三个记忆钩子

| 类型 | 一句话 |
|---|---|
| **反射型** | **照镜子** —— 你给什么，它当场原样返回来 |
| **存储型** | **下毒** —— 存进库里，谁打开谁中，你不用再出现 |
| **DOM 型** | **自产自销** —— 服务器全程没参与，浏览器自己把自己坑了 |

### ★ 存储型的根因有个坑

DVWA Low 档**其实调用了** `mysqli_real_escape_string()` —— 容易让人以为"它做了防护"。

> **但那个函数解决的是【SQL 层】的转义，它不会把 `<` 变成 `&lt;` —— 对 HTML 层毫无作用。**
>
> ### 核心心法：**转义必须匹配目标上下文。**
> 数据要进 SQL，就按 SQL 的规则转义；数据要进 HTML，就按 HTML 的规则转义。
> **在错误的层上做转义，等于没做。**

## 3. 网页中服务器 / 客户端 / 浏览器的分工

### 三个词，先分清"两个角色 + 一个具体程序"

| 词 | 是什么 | 在哪 |
|---|---|---|
| **服务器** | 提供内容的那台机器 + 程序（Apache/PHP） | 容器里 |
| **客户端** | "请求方"这个**角色** | 你的电脑 |
| **浏览器** | 客户端上**具体干活的那个程序**（Chrome） | 你的电脑 |

**`客户端` 是位置/角色，`浏览器` 是程序。** 客户端上除了浏览器还有操作系统、网卡 —— 但**只有浏览器懂 HTML 和 JS**。

### 一次访问的完整流水线

```text
【你的电脑 · 客户端】
 ①  地址栏 → 浏览器把 URL 拆开（协议 / 主机 / 端口 / 路径 / 查询串）
 ②  建立 TCP 连接，发出 HTTP 请求

════════════ 网络 ════════════

【容器里 · 服务器】
 ③  Apache 收到请求
 ④  看到是 .php → 交给 PHP 解释器
 ⑤  ★ PHP 执行：读数据库、拼字符串     ← 后端代码唯一活跃的时刻
 ⑥  产物是一段【纯文本 HTML】
 ⑦  Apache 加上响应头，发回去

════════════ 网络 ════════════

【你的电脑 · 客户端】
 ⑧  浏览器收到 HTML 文本：
       a. 解析 → 建 DOM 树
       b. 遇到 <script> → 交给 JS 引擎执行   ← 前端代码在这跑
       c. 布局 + 绘制 → 屏幕上出现页面
 ⑨  你看到页面
```

### ★ 记住这条分界线

> **PHP 的全部生命，只有第 ⑤ 步。**
> **你看到的任何东西，都是第 ⑥ 步之后的产物。**
> **服务器发完响应就"死"了 —— 页面到浏览器手里之后，它不再管你。**

### 这张地基能解释我已经踩过的所有坑

| 现象 | 用分工怎么解释 |
|---|---|
| `maxlength` 拦不住 Burp | 它是**浏览器**执行的，**服务器根本不知道有这个限制** |
| DOM 型的响应里没有 payload | 拼接是**浏览器**做的 |
| 前端表单校验不算安全措施 | 用户可以改**浏览器**，或干脆不用浏览器 |
| 同源策略为什么能生效 | 它是**浏览器**执行的规则，**服务器完全不知情** |
| "查看源代码"和 F12 看到的为何不同 | 前者是服务器发来的**文本**，后者是解析+执行后的 **DOM** |
| 日志里为什么没有 POST body | Apache 只记请求行和请求头，**body 它不记** |

**另外三个术语：**

| 术语 | 含义 |
|---|---|
| **前端** | 在**浏览器**里跑的那部分：HTML + CSS + JS |
| **后端** | 在**服务器**上跑的那部分：PHP/Python/Java + 数据库 |
| **静态 / 动态页面** | 静态 = 服务器直接发现成文件；动态 = **现场生成**（PHP 跑完才发） |

## 4. 添加请求头，加在哪里？（放在末尾会"无法解析"）

### HTTP 请求报文 = 四段，顺序固定

```text
① 请求行     GET /vulnerabilities/csrf/?password_new=aaa&... HTTP/1.1
② 请求头     Host: 127.0.0.1:8080
             User-Agent: Mozilla/5.0 ...
             Origin: http://evil.example        ← ★ 新加的头，加在这一堆里
             Referer: http://evil.example/attack.html
             Cookie: PHPSESSID=...; security=low
③ (空行)     ← ★ 头的【结束标记】
④ 请求体     （GET 没有；POST 有 —— 表单数据 / JSON）
```

### 为什么放在末尾会报错

**因为空行【之后】的东西，一律被当成【请求体】。**

```text
    GET /... HTTP/1.1
    Host: 127.0.0.1:8080
    Cookie: PHPSESSID=abc
                                ← 这个空行已经宣告"头结束了"
    Origin: http://evil.example  ← 你以为这是头

解析器看到的是：
    头 = Host, Cookie
    体 = "Origin: http://evil.example"
    → GET 请求本来不该有 body → 「无法解析」
```

### Burp 里的正确操作（4 步）

1. 找到任意一个**已有的头**（比如 `Cookie:`）
2. 光标放到那一行的**末尾**，按 `Enter` —— 在它**下面**新起一行
3. 输入 `Origin: http://evil.example`
4. **★ 不要碰最下面那个空行** —— 那是头的结束标记，不是"多打的空行"

### 自检三条

| 检查 | 说明 |
|---|---|
| 切到 Burp 的 **`Raw`** 视图 | 能看清空行的位置 |
| 头名**大小写不敏感**（`origin:` 也行） | 但**值敏感**：`http://Evil.example` ≠ `http://evil.example` |
| 头一律加在 **`Host:` 之后、空行之前** | 顺序随便，**位置不能错** |

### 真实字节长什么样

```text
'Host: 127.0.0.1:8080\r\nOrigin: http://evil.example\r\n\r\n'
                                          ↑ 头结束        ↑ body 开始
```

**那个 `\r\n\r\n` 就是"空行"** —— 头的最后一行结束后，再来一个换行，就是分隔符。

## 5. 攻击者骗来 cookie 后，是怎么"伪装成当前站点"的？

### ★ 结论：他不需要伪装成"站点"，他只需要伪装成【你】

> **而伪装的手段极其简单：把偷到的那串值，抄进自己请求的 `Cookie:` 头里。**

### 机制：服务器根本不查"来源"

```text
服务器的认人逻辑：
   读 Cookie: 头里的值 → 拿它去查会话 → "哦，是 admin 已登录"

它【不】看：
   ✗ 请求从哪个 IP 来
   ✗ 用什么浏览器 / User-Agent
   ✗ 请求是从哪个页面发起的（Origin / Referer）
```

> ### ★ 这正好接上 CSRF 那个 A/B 对照实验
> 实验证明：**把 `Origin` 换成 `http://evil.example`，服务器反应没有任何变化。**
> **既然服务器不检查来源，那么"从哪儿发请求"根本不重要 —— 只要 cookie 值对，从任何地方发都行。**

### 攻击者的三种做法

| 做法 | 具体操作 | 关键点 |
|---|---|---|
| **① 不用浏览器**（curl / Python / Burp） | 直接写 `Cookie: PHPSESSID=v5et1sgl...` | ★ **同源策略管不到** —— 他压根不是浏览器 |
| **② 用浏览器改 cookie** | F12 → Console → `document.cookie = "PHPSESSID=xxx; path=/"` → 刷新 | 浏览器就以为自己是那个用户了<br>（DVWA 没设 `HttpOnly`，所以走得通） |
| **③ 图形界面** | DevTools → Application → Cookies → 双击 value 改掉 | 最直观 |

### ★ 为什么同源策略管不到

> **SOP 是【浏览器】的规矩，不是【网络】的规矩。**
> （阶段 1 写 `dirscan.py` 时就已经用过这一点 —— 脚本可以随便扫任何站点，没有任何"同源"限制。）
>
> **攻击者只要不用浏览器，SOP 对他就是一纸空文。**

### CSRF vs 会话劫持（这张表要分清）

| | **CSRF** | **会话劫持**（偷到 cookie 之后用） |
|---|---|---|
| 用谁的浏览器 | **受害者的**（cookie 自动带上） | **攻击者自己的**（手动填 cookie） |
| 需要偷到 cookie 吗 | ❌ **不需要**（连值都不知道） | ✅ **需要** |
| 同源策略管得到吗 | **管得到**（所以只能"发"，不能"读"响应） | **管不到**（他不用浏览器） |
| 受害者在场吗 | **必须在**（要有有效会话） | 不需要（cookie 没过期就行） |
| 防御 | CSRF Token / `SameSite` | `HttpOnly` + `Secure` + 服务端会话绑定 |

> **CSRF 是"借你的浏览器"；会话劫持是"复制你的钥匙，回我自己家用"。**

### 动手验一遍（无痕窗口，3 分钟）

| 步 | 动作 |
|---|---|
| 1 | 正常窗口登录 DVWA |
| 2 | F12 → Console → `document.cookie` → 复制 `PHPSESSID=...` 那一段 |
| 3 | 打开**无痕窗口**（全新会话、未登录）→ 访问 `index.php` → 应该显示登录页 |
| 4 | 无痕窗口 F12 → Console → `document.cookie = "PHPSESSID=刚才复制的值; path=/"` |
| 5 | 刷新 → **应该直接是"已登录"状态** |

**完成标志**：能说出「**我什么都没输入密码，就变成了那个用户**」。

### ⚠️ 补一句：`HttpOnly` 到底挡住了什么

| 环节 | `HttpOnly` 挡得住吗 |
|---|---|
| **偷**（XSS 里 `document.cookie` 读不到） | ✅ **挡得住**（第 2 步做不了） |
| **用**（Burp / curl 直接写 `Cookie:` 头） | ❌ **挡不住** |

> **所以 `HttpOnly` 是"让偷变难"，不是"让用不可能"。**
>
> 真实世界里 cookie 泄漏的渠道不止 XSS：网络嗅探（明文 HTTP → 所以有 `Secure`）、
> 恶意浏览器扩展、日志泄漏、物理接触……
> **所以服务端还有一招：把会话和 IP / UA 绑定** —— 泄漏了也不好用（代价是可能误伤正常用户）。
## 6. `[::1]` 具体是什么域名

**短答：它不是域名，是一个 IP 地址字面量 —— IPv6 的环回地址（loopback），等价于 IPv4 的 `127.0.0.1`。**

### 拆开看

```text
[::1]
 │└┬┘
 │ └── ::1  = IPv6 环回地址
 └──── 方括号：URL 语法要求
```

### 方括号是干什么用的

**因为 IPv6 地址本身含冒号，而 URL 里的冒号已经用来分隔"主机"和"端口"了：**

```text
http://[::1]:18100/csrf_attack.html
        └─┬─┘ └─┬┘
        IPv6   端口
        ↑ 不包方括号的话，浏览器分不清哪个冒号是端口分隔符
```

**规则：URL 里出现 IPv6 地址，必须用方括号包起来。**
（IPv4 不用，因为它里面没有冒号：`http://127.0.0.1:18100/`）

### 三个名字的对照

| 写法 | 是什么 | 指向 |
|---|---|---|
| `127.0.0.1` | **IPv4 地址** | 本机 |
| `[::1]` | **IPv6 地址** | 本机（同一个环回口） |
| `localhost` | **主机名**（不是 IP） | 通常解析到 `::1` 和 `127.0.0.1` |

> ★ **三个都指向同一台机器，但对浏览器来说是三个不同的 host。**

### 为什么它在 CSRF 那一关很重要

**因为它能造出"跨站"：**

```text
http://[::1]:18100/  打  http://127.0.0.1:18101/
        ↑                        ↑
    发起方 host              目标 host
    → 两个不同的 host → 两个不同的【站】→ 【跨站】
    → SameSite=Lax 拦掉子资源请求的 cookie
```

**而 `127.0.0.1:18100` 打 `127.0.0.1:8080` 是【同站】**（只是跨源）→ cookie 照带。

> **那次实验就是故意用 `[::1]` 造"跨站"这个条件的** ——
> 用 `127.0.0.1` 换个端口只能造"跨源"，造不出"跨站"。

**实测（探针的原始输出）：**

```text
从 [::1]:18100 加载     → Sec-Fetch-Site: cross-site  → Cookie=(没有 Cookie)
从 127.0.0.1:18100 加载 → Sec-Fetch-Site: same-site  → Cookie=PHPSESSID=...; probe=1
```

## 7. 我用的 Edge 浏览器也是谷歌内核吗

**是的 —— 从 2020 年 1 月起（Edge 79），Edge 换成了 Chromium 内核。**

### 先分清四个名字

| 名字 | 是什么 |
|---|---|
| **Chromium** | **开源项目**，Google 主导；提供渲染引擎 + JS 引擎 |
| **Chrome** | Google 在 Chromium 之上**加了自己的东西**（账号同步、Google 服务） |
| **Edge** | 微软在 Chromium 之上**加了微软的东西**（微软账号、Bing、Copilot） |
| **Edge Legacy**（2020 前） | ❌ 那是微软自己的 **EdgeHTML** 内核，**不是** Chromium |

**所以 Chrome 和 Edge 共用：**

- 渲染引擎 **Blink**
- JS 引擎 **V8**
- DevTools（基本一样）
- ★ 那一套安全机制：`SameSite` 默认值、`Sec-Fetch-*` 头、`Referrer-Policy` 默认值

### ★ 对我的实际影响（3 条）

1. **我做的所有实测结论，对 Edge 一样成立** ——
   `SameSite=Lax` 默认、`Sec-Fetch-Site`、`Referrer-Policy: strict-origin-when-cross-origin`
   都是 **Chromium 的行为**，不是"Chrome 专有"。
2. **版本号不同** —— 新特性可能先后差几个月。
3. **cookie 库位置不同，但结构一模一样（实测）：**

```text
Chrome: C:\Users\yihai\AppData\Local\Google\Chrome\User Data\Default\Network\Cookies
Edge  : C:\Users\yihai\AppData\Local\Microsoft\Edge\User Data\Default\Network\Cookies
                                                        └──── 结构完全同构 ────┘
```

**同一套 profile 目录布局、同一个 SQLite 文件名** —— 这就是"同内核"的物证。

### 其他同类 / 异类

| 浏览器 | 内核 |
|---|---|
| Chrome / Edge / Brave / Opera / Vivaldi / 360极速 / QQ（部分） | **Chromium（Blink + V8）** |
| **Firefox** | **Gecko**（自己的） |
| **Safari** | **WebKit**（自己的） |

> ### ★ 这对做 Web 安全很实际
> **"浏览器默认行为"要按【内核家族】来问，而不是按品牌。**
> 以后你写 payload 或做防御，要问的是"**这个内核**怎么处理"，
> 而不是"Chrome 怎么处理"。**（Chrome 的结论对 Edge 成立，对 Firefox 不一定。）**
